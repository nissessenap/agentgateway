MCP login through the gateway: callback proxy (prototype)

Question: if agentgateway proxies the whole authorization round trip (/authorize → Keycloak → gateway /callback → client, plus /token), can it stay stateless, make RFC 9207 iss checks pass, and avoid turning into an open redirector or code-theft vector? Option 1 from issue #1. Pick a scenario tab or click freely. Everything is simulated in the page; nothing hits a network.

Deployment: "Gateway" below is agentgateway itself, not a separate service. The new endpoints (…/authorize, …/callback, …/token) live under the AS metadata path the gateway already serves and would be handled in handle_mcp_request in mcp/auth.rs, next to today's Entra /authorize and /token proxies.

    Troublemakers

    Design choices shown here, and open questions for maintainers

    • Stateless: the client's redirect_uri, state, client_id and an expiry ride inside a gateway-sealed state (AEAD in real life; a checksum stand-in here). Multi-replica gateways need a shared key. Where does it come from?
    • Code wrapping: the gateway hands the client a sealed code that holds Keycloak's code plus the original redirect_uri. At /token it checks that the client's redirect_uri matches (RFC 6749 §4.1.3) and swaps in its own callback, all without storing anything. Alternative: pass Keycloak's code through as-is and skip the check.
    • Redirect allowlist is now the gateway's job. Keycloak only sees the gateway callback, so it can't protect client redirect URIs anymore. Proposed policy: loopback (any port, RFC 8252) plus a configured list. See the "Why the redirect check matters" tab. With a proxied real DCR (no clientId), the gateway would also have to rewrite redirect_uris at registration time.
    • IdP setup: the Keycloak client must register the gateway callback URL as a redirect URI.
    • Gateway checks Keycloak's iss on the callback, so RFC 9207 protection is kept on the gateway↔IdP leg, and the client gets iss = gateway issuer.
    • Unchanged: access tokens are still Keycloak's (iss = Keycloak), so JWT validation config stays as is. Refresh tokens pass straight through /token. The existing Entra /authorize//token proxies (strip resource, inject secret) would become per-provider tweaks on this shared path.
    • For every provider, or opt-in?
